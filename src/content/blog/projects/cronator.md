У меня сотни скриптов. Выгрузки, сверки, отчёты, мелкие боты, всё то, что должно запускаться по расписанию и чего никто не замечает, пока оно работает. Самое простое место для них было на виртуальном сервере, где уже стоял общий cron с коллегами.

Туда я класть их не хотел. Общий crontab значит общий Python, общие пакеты и одна строка в файле, которую кто-то поправит, не зная, что она твоя. Достаточно одному человеку обновить библиотеку для своего скрипта, чтобы у других утром оказались пустые отчёты. А главное, cron молчит. Скрипт упал в три ночи с ошибкой импорта, и ты узнаёшь об этом, когда кто-то спросит, почему отчёт не пришёл.

Airflow для такой задачи слишком большой. Брокер, воркеры, DAG и отдельная команда, чтобы всё это поддерживать. Мне нужно было что-то между ними, и я написал [Cronator](https://github.com/aa-blinov/cronator).

Это один процесс с веб-интерфейсом. Каждому скрипту задаёшь расписание в формате cron, версию Python и список пакетов. При первом запуске Cronator сам собирает ему отдельное окружение через `uv`, и пакеты одного скрипта больше не ломают другой. Каждый запуск остаётся строкой в истории: вывод, ошибки, код выхода, длительность. Скрипт упал, приходит письмо или вебхук. Роли две: администратор и наблюдатель.

Его ценность в том, что в нём нет платформы. Ни брокера, ни воркеров, ни графа задач. Поставил контейнер с базой, открыл страницу, добавил скрипт.

```bash
git clone https://github.com/aa-blinov/cronator
cd cronator
cp .env.example .env   # ADMIN_PASSWORD, SECRET_KEY, POSTGRES_PASSWORD
docker compose up -d
```

Если сервер лежал как раз тогда, когда скрипт должен был запуститься, Cronator после подъёма запишет пропущенные запуски и покажет их на главной. Там же отдельно видны скрипты, у которых семь дней не было ни одного успешного запуска. Вывод идущего скрипта можно смотреть в браузере в реальном времени, а каждая правка кода сохраняется версией, к которой можно откатиться.

Начинать с пустого файла не обязательно: в Cronator есть 19 готовых шаблонов. Проверка SSL-сертификатов, бэкап PostgreSQL и MySQL, проверка диска и DNS, уведомления в Telegram, Slack, ntfy и Pushover.

Ошибка, о которой никто не узнал, опаснее ошибки, которая громко упала. Поэтому о падении Cronator сообщает сам.

Мои скрипты живут отдельно от общего сервера, каждый в своём окружении. Падать они теперь обязаны громко.
